Status: Accepted (overseer/Brandon standing ruling, 2026-08-23; in force until
v0.1.0 ships). This records a release-governance decision — what work counts
this cycle — not a new product or wire-contract boundary. It changes no served

Sets the priority frame for the enterprise tracks already governed by
[ADR-0030](0030-the-authorization-boundary.md) (the authorization boundary),
[ADR-0033](0033-the-feedback-agent.md) (the feedback/write-back agent),
[ADR-0035](0035-layered-deployment-configuration.md) (layered deployment

release cares about now.

## Context

We are shipping a v0.1.0 enterprise-readiness release this week. Recent
throughput over-produced low-value new-surface PRs — breadth that did not move a
core capability closer to enterprise quality. The release bar is the opposite:
fewer beads, each **hardening and testing** a core feature to enterprise
quality. Quality, hardening, and tests take precedence over new surface area.

## Decision

1. **The core product is connections + embedding serving + the suggestions on
   top.** These are what we sell; the release solidifies and hardens them to
   release quality rather than widening the surface around them.
2. **Prioritized tracks — drive forward, each hardened and tested:**
   1. auth and multi-repo support;
   2. the write-back agent and the staleness-check agent
      ([ADR-0033](0033-the-feedback-agent.md));
   3. Slack integration for those agents;
   4. user-based authorization granularity (per-user permissions), within the
      [ADR-0030](0030-the-authorization-boundary.md) boundary.
3. **Deprioritized — do not spend cycles hardening or extending:** the DataHub
   and Superset connectors. They are weak features and are not this release's
   focus. Keep them working; do not polish or widen them.
4. **Every bead slung and every review this cycle is judged against this
   focus.** Core hardening with tests is rewarded; non-core work — connector
   polish, or new-surface UI that does not serve a prioritized track — is
   deferred, not merged as incidental scope.

## Enable-gates and honest status

Implementation status is marked honestly, not aspirationally. Several
prioritized items are gated on open overseer activation or authorization forks,
and those gates — not this ADR — are what let the items ship:

- **Staleness-check agent activation** is gated on the open forks
  **hy-y588** and **hy-kh9k**; the agent is not enabled until they clear.
- **Per-user authorization granularity** is gated on the
  [ADR-0030](0030-the-authorization-boundary.md) F1–F5 forks tracked by
  **hy-tjow**; per-user permissions are not enforced until that authz work is
  ratified and wired.

Until an enable-gate clears, the corresponding track ships default-off,
byte-identical, and honestly labeled as gated — the same discipline
[ADR-0030](0030-the-authorization-boundary.md) applies to the auth enable-flip.

## Consequences

- Reviewers reward core hardening and tests and flag or defer non-core
  (connector or new-surface) work; a PR that widens surface without hardening a
  prioritized track is out of scope for the cycle.
- The mayor cites this ADR when slinging beads and ruling on scope, so a scope
  call has a written basis rather than a per-bead judgment.
- DataHub and Superset connector work stalls deliberately for the cycle; that is
  the intended trade, not neglect, and it is revisited after v0.1.0.
- The record is time-boxed: it is in force until v0.1.0 ships, after which a
  newer ADR sets the next cycle's frame rather than this one being rewritten.

## Rejected alternatives

- **Keep maximizing PR throughput.** Breadth without hardening is what this
  ruling corrects; a green count of shallow PRs is not enterprise readiness.
- **Harden every feature evenly, including the connectors.** Finite cycle;
  spreading effort across weak, non-focus features starves the tracks we sell.
- **Leave the focus as an informal directive.** An unwritten priority cannot be
  cited in a review; recording it as an ADR makes "is this in scope?" answerable
  against a durable decision.
