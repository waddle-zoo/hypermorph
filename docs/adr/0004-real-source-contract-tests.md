# 0004: Compatibility is proven by real-source contract tests, not hand-written fixtures alone

Status: accepted.

## Context

`tests/fixtures/superset/{4.0.0,6.1.0}/` are hand-written snapshots, not
generated by a real Superset instance. The `6.1.0` fixture set used
pre-6.1 field names (`datasource_name`, `position_json`, nested
`database`), so a passing test proved only that two hand-written payloads
reduce to the same expected objects — not that either shape matches a
real export (`docs/research/FACT_CHECK_2026-07-25.md` Blocker C).

## Decision

Hand-written fixtures are supplemental only, never compatibility proof.
The v0 compatibility policy (`docs/architecture.md` §4-5): a Superset
version/transport is supported after a real pinned upstream instance
(Docker) passes the connector contract suite — unmodified export ZIP
retained, source-version/capability metadata captured, live-mode and
bundle-mode normalization compared against the same source assets.

The existing hand-written fixtures and their tests are kept (not deleted
— `hy-gh-35` non-goals) as regression coverage for the historical
`hyperset.bridge`/`hyperset.compat` mapping code, clearly marked
historical (`tests/fixtures/superset/README.md`), not as evidence for the
current connector.

## Consequences

- Generating real fixtures requires a running Docker Superset instance
  (`hy-gh-37`/`hy-gh-27` Phase C) — this work is sequenced after those
  land, not before.
- Until then, `hyperset.connectors.superset`'s field-shape corrections
  are based on verified real source inspection
  (`docs/research/superset-metadata-models.md`, checked against
  `apache/superset@6.1.0`), not on hand-written fixtures claiming
  compatibility.
